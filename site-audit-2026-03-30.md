## Performance

### 1. LCP preload pointed at the wrong image ✅ Fixed
**Severity: High**

`index.html` had a `<link rel="preload">` for `images/BB-030/bb-italia-14-800w.jpeg` but the first card in the grid was the Rove Concepts Milo (`RC-043/rove-concepts-01`). The browser was downloading the B&B Italia image ahead of everything else, then discarding it when the actual first card loaded. This directly delayed Largest Contentful Paint.

**Fix applied:** Updated the preload in `index.html` to `RC-043/rove-concepts-01-800w.jpeg`. Also added `<!-- LCP_PRELOAD_START -->` / `<!-- LCP_PRELOAD_END -->` markers and updated `build.js` to regenerate this tag automatically on every build so the preload always tracks the first item in the available array. It will never go stale again.

---

### 2. Google Fonts blocks initial render
**Severity: Medium**

The async font-loading pattern (`onload="this.rel='stylesheet'"`) is already in place — this is good. However, Playfair Display and Inter are loaded from Google Fonts, which requires a DNS lookup + TCP handshake to `fonts.googleapis.com` and `fonts.gstatic.com` before the page text can render in brand fonts. The `preconnect` hints at the top of `<head>` help, but the fonts themselves must be fetched before they can be used.

**Options, in order of effort:**
- (Low effort) Consider self-hosting the fonts. Run `google-webfonts-helper.io`, download the two fonts, add them to `css/`, and replace the Google Fonts link with a local `@font-face`. This eliminates the external dependency entirely and typically shaves 300–600ms off perceived render time on mobile.
- (Lowest effort, partial win) Subset the fonts to only the characters used. Playfair Display is only used for headings — the full character set is wasteful.

---

### 3. No explicit width/height on JS-rendered carousel images
**Severity: Low–Medium**

The static fallback HTML (generated by `build.js` for crawlers) includes `width="800" height="600"` on the first image, which prevents layout shift during initial load. However, the `buildCarousel()` function in `shared.js` does not include `width` or `height` attributes on the `<img>` elements it generates. When JavaScript replaces the static fallback with the carousel, there could be a brief layout shift if the CSS `aspect-ratio: 4/3` hasn't been applied yet.

In practice, the carousel container has `aspect-ratio: 4/3` which holds the space even before the image loads, so CLS impact is likely minimal. But it's worth adding `width="800" height="600"` to carousel images in `buildCarousel()` as a defensive measure.

**Fix (in `js/shared.js`):** In `buildCarousel()`, add `width="800" height="600"` to the `<img>` tag string. Re-minify: `node build.js`.

---

### 4. Listing pages load all carousel images in HTML
**Severity: Low**

The Rove Concepts listing page has 12 images all written into the HTML carousel at page load — each with a `<picture>` element containing WebP and JPEG srcsets. Non-first images have `loading="lazy"` so they won't download immediately, but they all exist in the DOM. At 12 images, this is reasonable. Watch this as inventory grows: if listings ever hit 20+ images, consider a JS-driven "load-on-swipe" approach.

## Mobile Usability

### 5. Phone number disappears on mobile ⚠️ Not yet fixed
**Severity: High — direct conversion impact**

The `.nav-contact` div (which contains the `780-965-1477` phone link) is hidden at `≤ 768px` with no mobile equivalent. On mobile, a buyer has no immediately visible way to call or text from the homepage or sold/guide pages unless they open a listing or find the Sell page.

**Fix:** Add the phone number as the last `<li>` in the `<ul class="nav-links">` with a mobile-only visibility class. This way it appears in the hamburger dropdown on mobile.

In every page's nav `<ul>`:
```html
<li class="nav-phone-mobile"><a href="tel:7809651477">780-965-1477</a></li>
```

In `css/styles.css` (then regenerate `styles.min.css`):
```css
.nav-phone-mobile { display: none; }

@media (max-width: 768px) {
  .nav-phone-mobile {
    display: list-item;
    font-size: 0.95rem;
    font-weight: 600;
    letter-spacing: 0;
    text-transform: none;
    border-top: 1px solid var(--color-border);
    padding-top: 16px;
    margin-top: 4px;
  }
  .nav-phone-mobile a {
    color: var(--color-text);
  }
}
```

This needs to be added to: `index.html`, `sold/index.html`, `sell/index.html`, `about/index.html`, `guides/index.html`, all `guides/*/index.html` files, and the nav template inside `build.js` (so listing pages get it too).

### 6. Credibility strip text is too small on mobile
**Severity: Medium**

At `≤ 768px`, the credibility strip font drops to `0.65rem` (≈ 10.4px at default 16px root). At `≤ 400px`, it drops further to `0.58rem` (≈ 9.3px). Both are below the WCAG 2.1 minimum of 12px for body text and below iOS minimum tap-readable threshold.

The strip content ("40+ Pieces Sold | ★ 4.9 Rating | Proudly Edmonton Owned & Operated") is trust-building social proof. Shrinking it to the point of illegibility defeats the purpose.

**Fix:** Minimum `0.75rem` (12px) at all breakpoints. If it wraps to two lines at that size, allow it — the wrap is better than illegibility. Remove `flex-wrap: nowrap` at mobile so the text can reflow.

In `css/styles.css` mobile block:
```css
@media (max-width: 768px) {
  .credibility-strip {
    font-size: 0.75rem;  /* was 0.65rem */
    padding: 8px 16px;
    gap: 10px;
    flex-wrap: wrap;     /* was nowrap — allow wrapping */
  }
}

@media (max-width: 400px) {
  .credibility-strip {
    font-size: 0.72rem;  /* was 0.58rem */
  }
}
```

### 7. Newsletter form has no label
**Severity: Medium — accessibility + mobile autocomplete**

The email `<input>` in every newsletter form has no `<label>`. It relies on placeholder text ("Your email address"), which disappears when the field is focused and is not read consistently by screen readers. It also means iOS/Android autofill can't reliably identify the field type.

**Fix:** Add a visually hidden label to every newsletter form. Replace:
```html
<input type="email" name="email_address" placeholder="Your email address" required>
```
with:
```html
<label for="newsletter-email" class="sr-only">Email address</label>
<input type="email" id="newsletter-email" name="email_address" placeholder="Your email address" autocomplete="email" required>
```

The `.sr-only` class is already defined in `styles.css`. The `autocomplete="email"` attribute triggers the correct keyboard on mobile and enables password manager/autofill.

This needs to be applied to: `index.html`, `sold/index.html`, `about/index.html`, `sell/index.html`, all guide pages, and the listing page template in `build.js`.

**Note:** Each page can only have one element with `id="newsletter-email"`, which is fine since there's one form per page.

### 8. Listing page: CTA order on mobile
**Severity: Low**

On listing pages, the price and CTA buttons appear below the description (which can be long). On mobile, a motivated buyer has to scroll past 400–600 words before reaching "Text to Secure." The CTAs are actually placed above the description in the HTML/CSS layout, but the description section is currently under a `<details>` element that opens by default (`open` attribute), meaning it's expanded on load.

Consider whether `<details open>` is the right default on mobile. Keeping Description collapsed by default on mobile would surface the CTAs faster. The existing collapsible pattern is good — it just needs a `media query`-aware default.

## SEO & Discoverability

### 9. llms.txt missing ✅ Fixed
**Severity: High for AI discoverability**

AI assistants (ChatGPT, Perplexity, Claude, Gemini) increasingly crawl `llms.txt` at the domain root to understand what a site is and what's on it. Without one, AI tools have to infer the business from page content alone — and may miss pages or misclassify the business.

**Fix applied:** Created `/llms.txt` with a plain-text business description, contact details, and a complete list of key page URLs including all guides.

---

### 10. priceValidUntil will expire
**Severity: Medium**

All Product schemas have `"priceValidUntil": "2026-06-27"`. After that date, Google's Rich Results validator will flag the products as having expired pricing data. This doesn't cause immediate de-indexing but can suppress product rich results in search.

**Fix:** Either (a) update `priceValidUntil` to a rolling 90-day date every time you run the build, or (b) change `build.js` to set it dynamically. The dynamic fix:

In `build.js`, find where `priceValidUntil` is set in `generateProductSchemas()` and `generateListingPage()`, and replace the hardcoded date string with:

```javascript
function priceValidUntil() {
  var d = new Date();
  d.setDate(d.getDate() + 90);
  return d.toISOString().split('T')[0];
}
```

Then use `priceValidUntil()` wherever the date string appears.

### 11. Listing page breadcrumb skips the inventory level
**Severity: Low**

Listing page breadcrumbs show `Home / [Item Title]` — two levels. A three-level breadcrumb (`Home / Available / [Item Title]`) is more informative for Google and users.

**Fix in `build.js`** (BreadcrumbList schema and visible breadcrumb HTML in `generateListingPage()`): Add "Available" as position 2 pointing to `https://edmonton-refreshed.com/`.

### 12. robots.txt doesn't address AI bots
**Severity: Low — informational**

The current `robots.txt` allows all crawlers with no restrictions, which is correct. AI crawlers like GPTBot, ClaudeBot, and PerplexityBot respect `robots.txt`. Since you want AI crawlers to index this site (the guides and inventory are directly useful for AI answers about furniture in Edmonton), no change is strictly necessary.

If at any point you wanted to block a specific AI bot, the syntax is:
```
User-agent: GPTBot
Disallow: /
```
For now, leave it open.

## Accessibility

### 14. No skip-to-content link
**Severity: Medium**

Screen reader and keyboard users must tab through the entire fixed nav (logo + 5 nav links + phone number + hamburger button = 8 focusable elements) before reaching the main content on every page. A skip link is the standard fix and takes one element to implement.

**Fix:** Add as the very first element inside `<body>` on every page:
```html
<a href="#main-content" class="skip-link">Skip to main content</a>
```

And add `id="main-content"` to the `<main>` element. In `css/styles.css`:
```css
.skip-link {
  position: absolute;
  top: -100%;
  left: 0;
  padding: 8px 16px;
  background: var(--color-accent);
  color: #fff;
  z-index: 9999;
  text-decoration: none;
  font-size: 0.875rem;
}
.skip-link:focus {
  top: 0;
}
```

---

### 15. FAQ section is outside `<main>`
**Severity: Low**

On the homepage, `<section class="faq-section">` and `<section class="service-area-note">` sit outside `</main>` in the footer area of the page. The `<main>` landmark closes before these sections. Screen reader users navigating by landmark will skip past the FAQ and service area note.

**Fix:** Either move these sections inside `<main>`, or wrap them in an explicit `<section aria-label="FAQ">` landmark. The simplest fix is to extend the `</main>` closing tag to include these sections.

---

### 16. Missing `aria-expanded` on nav toggle
**Severity: Low**

The `<button class="nav-toggle">` opens and closes the mobile nav but doesn't communicate its state to screen readers. A screen reader user has no way to know whether the nav is currently open or closed.

**Fix in `js/shared.js`:** When toggling the nav, also toggle `aria-expanded`:
```javascript
navToggle.setAttribute('aria-expanded', navLinks.classList.contains('open') ? 'true' : 'false');
```
And add `aria-expanded="false"` as the default attribute on the button in all HTML files.
